# Effect-TS Rewrite — Phase 1 + Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Execute Phase 1 (clear the deck — delete backend + frontend implementation code, keep tooling + contract docs) and Phase 2 (write Effect-ecosystem assessment ADR drafts under `docs/adrs/draft/`) of the Effect-TS rewrite, leaving the repo in a state where Phase 3 (first vertical slice) can begin against a coherent set of stack decisions.

**Architecture:** Two phases, executed sequentially on `main` (no PR, solo repo). Phase 1 is a controlled wipe with cross-package coupling audit, lint-gate guards (`WIPE_IN_PROGRESS=1`), and verified-green `make lint` / `make test` / `make test-unit` at the end of each commit. Phase 2 produces 11 ADR drafts under `docs/adrs/draft/` (status `proposed`, no `verified_by` yet), some informed by ≤4h spikes. ADR drafts get promoted to numbered slots (`docs/adrs/0011-*.md` … `0021-*.md`, status `accepted`) only in Phase 3 alongside the code they govern.

**Tech Stack:** TypeScript, Effect-TS (target), pnpm + turbo + Bun (inner loop), Make (orchestration), prek (pre-commit), Biome + tsc + 14+ custom lint checks (gate). Existing stack to be deleted: TanStack Start, Hono, tRPC, Prisma, BullMQ, Better-Auth, ws, nodemailer, pino, Zod 4. (Decisions on what each gets replaced with land in Phase 2 ADR drafts.)

**Predecessor docs (read in order):**
1. [`docs/superpowers/specs/2026-04-28-effect-rewrite-phase-1-design.md`](../specs/2026-04-28-effect-rewrite-phase-1-design.md) — the design doc this plan executes

**Constraints (non-negotiable):**
- No `--no-verify` on commits. Pre-commit hook is read-only (`make lint`); fix lint failures, don't bypass.
- `make lint` green at end of every commit.
- No GitHub PRs. Merge to `main` directly + `git push origin main`.
- Use `pnpm` CLI for version bumps (no hand-edited `package.json`).
- Bun stays inner-loop only. Don't reintroduce Bun in Dockerfiles or production paths.

**Rollback:** `git reset --hard stable-pre-effect && git push --force-with-lease origin main` (requires user authorization at the moment it's invoked, not pre-authorized by this plan). The tag `stable-pre-effect` and branch `stable/pre-effect` are immutable rollback points.

## Task 3: Set up `WIPE_IN_PROGRESS` lint-guard infrastructure

**Files:**
- Create: `.config/lint.env`
- Modify: root `package.json` (lint scripts) — wrap with env loader

- [ ] **Step 1: Create the env file**

```bash
cat > .config/lint.env <<'EOF'
# Set by Phase 1 of the Effect-TS rewrite. See:
#   docs/superpowers/specs/2026-04-28-effect-rewrite-phase-1-design.md
# Removed in Phase 3 once the first vertical slice restores the patterns
# that the gated lint checks police.
WIPE_IN_PROGRESS=1
EOF
```

- [ ] **Step 2: Decide the env-loading mechanism**

Inspect how the existing root lint scripts run:

```bash
grep -A1 '"lint":\|"lint:' package.json | head -40
cat Makefile | grep -A2 'lint:' | head -20
```

Pick the mechanism that requires the smallest diff. Options ranked by simplicity:
1. Make-level: prefix the `lint` target in `Makefile` with `set -a; source .config/lint.env; set +a;` so all child processes inherit `WIPE_IN_PROGRESS`. (Likely simplest.)
2. Per-script in `package.json`: add a tiny `dotenvx run --env-file=.config/lint.env --` wrapper to each gated check script. (More targeted but more diff.)
3. Add `dotenv-cli` as a dev dep and wrap. (Most explicit, biggest diff.)

Pick option 1 unless `Makefile` complications force otherwise.

- [ ] **Step 3: Apply the chosen mechanism**

For option 1, edit the `lint` target in `Makefile` (the one prek pre-commit hook calls — confirm the exact target name first via `grep -B1 -A3 '^lint:' Makefile`). Add the `set -a; source .config/lint.env; set +a;` line at the top of the target's recipe.

- [ ] **Step 4: Verify the env propagates**

Add a temporary `console.error("WIPE_IN_PROGRESS=", process.env.WIPE_IN_PROGRESS)` to one lint check (e.g., `packages/lint/src/check-no-cwd.ts`), run `make lint`, confirm the value prints `1`, then revert the temporary line.

- [ ] **Step 5: Commit**

```bash
git add .config/lint.env Makefile
git commit -m "$(cat <<'EOF'
chore(rewrite): add WIPE_IN_PROGRESS lint-guard infrastructure

Phase 1 of the Effect-TS rewrite (per design doc
docs/superpowers/specs/2026-04-28-effect-rewrite-phase-1-design.md)
needs to disable lint checks whose patterns disappear with the
deletion of backend + frontend implementation code.

WIPE_IN_PROGRESS=1 is set in .config/lint.env and sourced into the
Makefile lint target. Affected checks gain a top-of-file early-return
guard in subsequent commits. Both the env file and the guards are
removed commit-by-commit in Phase 3 as the first slice restores
the patterns those checks police.

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
EOF
)"
```

**Success criterion:** `make lint` still passes. `WIPE_IN_PROGRESS=1` is in scope inside lint check scripts. Commit lands cleanly without any pre-commit failures.

### Task 14: ADR draft 0013 — DB access

**Topic:** DB access layer. Prisma wrapped behind a `Db` Layer vs `@effect/sql`.

**Default lean:** Wrap Prisma. Migration cost without ergonomic win; the rewrite preserves the `prisma/schema.prisma` contract; `@effect/sql` would mean rewriting the schema model.

**Spike optional (≤2h):** Build a 2-procedure example (one read, one write-with-tx) using `Effect.tryPromise` over the Prisma client inside a `Db` Layer. Measure: ergonomic friction at the call sites, error-tagging burden, transaction composition.

**Files:** Create `docs/adrs/draft/0013-db-access.md`. Commit.

### Task 15: ADR draft 0014 — Schema validation

**Topic:** Schema/validation library. Zod 4 vs Effect Schema, used on both server and (per Q4) client.

**Default lean:** Replace Zod with Effect Schema. Server-side this is unambiguous; client-side bundle cost is real but acceptable per Q4.

**Spike required (≤4h):**
- Build a representative form schema (e.g., a 6-field todo creation form with discriminated-union validation) in both Zod 4 and Effect Schema in `/tmp/effect-rewrite-spikes/0014-schema/`.
- Measure: bundle size delta on a Vite build (`vite build`, then `du -sh dist/`), parse-error ergonomics, integration with TanStack Form.
- Reference Effect bundle issues #5967 and #5317 for tree-shaking gaps.

**Files:** Create `docs/adrs/draft/0014-schema-validation.md`. Commit.

### Task 16: ADR draft 0015 — Queue

**Topic:** Background job queue. BullMQ wrapped behind a `Queue` Layer vs `@effect/cluster` `ClusterQueue` (when ready).

**Default lean:** Wrap BullMQ. `ClusterQueue` is not yet production-ready; BullMQ + a `Queue` Layer + `Schedule`-driven retries inside handlers is the pragmatic pick.

**Spike optional:** Confirm the current state of `@effect/cluster` and `ClusterQueue` (npm version, examples, docs status). Inline as the ADR's "ecosystem state" section.
